МЕТОДИКА СРАВНЕНИЯ С GNSS-ЭТАЛОНОМ

1) Чекер организаторов в ROS 2 (основной результат). hackathon_solution_checker собран из исходников организаторов в Docker (ROS 2 Humble) вместе с нашим пакетом, запуск scripts/run_checker.sh --measure.
– Эталон: /localization/kinematic_state (nav_msgs/Odometry, 50 Гц, кадр map), точка base_link на pathgraph в 9.873 м впереди главной антенны, z по pathgraph.
– Сопоставление: ApproximateTimeSynchronizer, slop 0.05 с, очередь 100, отдельно для /result/velocity и /result/position.
– Метрики: скорость twist.linear.x (RMSE, max), положение (RMSE по x, y, z и по 3D-расстоянию).
– Прогон: весь тестовый bag 30618_88aea4d9 (≈22 мин) в реальном времени (ros2 bag play -r 1.0), нода с параметрами по умолчанию: vehicle_id 30618, точка base_link, кадр map, GNSS-коррекция положения включена.

2) Офлайн-эмуляция чекера (tools/checker_sim.py): bag проходит через тот же класс Pipeline, что в ROS-ноде, с тем же эталоном и синхронизатором; так сравниваются 7 конфигураций. Эмуляция совпадает с настоящим чекером: 3D RMSE 1.115 против 1.111 м.

3) Кросс-валидация на датасете (tools/run_cv.py + tools/evaluate.py).
– Прогоняются все 122 bag (0 ошибок), метрики считаются по 60 оценочным заездам (уникальные записи с ≥ 60 с RTK): 30 T2S и 30 S2T, 49 на вагоне 30618 и 11 на 30639. 6 групп «вагон_день» (фолды leave-one-group-out), метрики выводятся и по группам, направлениям, вагонам.
– Эталон: фиксы GNSS RTK главной антенны со статусом 2, скорость эталона из GNSS.
– Сопоставление: для каждой точки эталона берётся выход с ближайшим header stamp, если разница не больше 0.05 с.
– GNSS подаётся только в окне старта, первые 10 с после первого fix (режим скрытой проверки). Дальше работают только тележки, команда контроллера и карта. Вариант burst: 30 с на старте, затем пачка 1.5 с каждые 120 с (редкий GNSS по ходу рейса).
– Точка выхода на CV: главная антенна, без задержки скорости, поэтому числа CV с числами чекера напрямую не сравниваются.
– Метрики: RMSE и MAE скорости по всему заезду; смещение на переходных режимах (наибольший модуль среднего смещения по режимам разгон / торможение / стоянка / движение); along-track: разность дуговых координат оценки и эталона на карте, RMSE, среднее модуля и max; cross-track RMSE; e3d: средняя 3D-ошибка за прогон; дрейф: 2D-ошибка в последней точке в % пройденного пути. По 60 заездам берутся медиана и среднее.

ТАБЛИЦЫ ОШИБОК

Чекер организаторов, ROS 2 в Docker, bag 30618_88aea4d9, итоговый образ, 38 437 пар:
• скорость: RMSE 0.0324 м/с, max 0.302 м/с;
• положение x / y / z: RMSE 0.904 / 0.645 / 0.037 м;
• положение 3D: RMSE 1.111 м, max 14.02 м.

Эмуляция чекера на том же bag (3D RMSE; RMSE скорости):
• итоговая версия: 1.11 м (медиана 0.50, p95 1.98 м); 0.0335 м/с;
• без GNSS-коррекции по ходу рейса: 7.16 м; 0.0335 м/с;
• GNSS только первые 35 с: 7.02 м; 0.0335 м/с. Первые 8 минут ошибка 0.3–1.6 м, на последней минуте 30.3 м: без GNSS хвост после конца карты идёт по ветке петли по умолчанию;
• без разворотных петель: 23.09 м;
• версия до уточнений организаторов (историческое сравнение): 24.24 м; 0.0566 м/с.
Скорость от GNSS не зависит: с коррекцией и без неё она совпадает побитово.

Кросс-валидация, 60 заездов, медиана / среднее.
F4_final (GNSS только первые 10 с):
• скорость: RMSE 0.0295 / 0.0511 м/с; MAE 0.0206 м/с (медиана); смещение на переходных режимах 0.0121 / 0.0229 м/с;
• along-track: RMSE 1.98 / 3.15 м, среднее модуля 1.52 / 2.47 м, max 8.14 / 11.9 м; cross-track RMSE 0.205 / 0.475 м;
• e3d 1.66 / 2.80 м; дрейф 0.047 / 0.127 % пути.
F4_final_burst (редкий GNSS по ходу рейса, корректируется только положение):
• along-track RMSE 0.834 / 1.97 м; e3d 0.820 / 1.47 м; дрейф 0.0125 / 0.121 %; скорость та же.
Базовая линия B1_naive (среднее двух тележек, интеграл пути, без модели):
• along-track RMSE 2.81 / 5.91 м; e3d 5.23 / 8.57 м; дрейф 0.471 / 1.17 %; скорость RMSE 0.0541 / 0.0728 м/с.
Фильтр Калмана без тяговой модели (B1_naive_kf) на чистых данных даёт ту же скорость (0.0296 м/с); модель выигрывает при отказах датчиков (см. УСТОЙЧИВОСТЬ).

Скорость по режимам (F4_final, медиана RMSE): разгон 0.0346, торможение 0.0332, движение 0.0338, стоянка 0.0122 м/с; модуль смещения в разгоне 0.0097, в торможении 0.0067 м/с. По направлениям: S2T 0.0298, T2S 0.0286 м/с.

Абляции (CV, выключен один механизм): без разворотных петель e3d 1.66 → 4.66 м, дрейф 0.047 → 0.324 % (медианы); без TRN (сопоставление с профилем уклона) среднее along-track RMSE 3.15 → 4.49 м; без адаптации коэффициентов тяги и торможения медиана along-track RMSE 1.98 → 2.74 м.

УСТОЙЧИВОСТЬ

tools/robustness.py: 12 заездов × 28 сценариев = 336 прогонов с отказами, 0 падений, 0 нечисловых выходов, 0 отрицательных скоростей. Вносились: молчание одной или обеих тележек (5–60 с, в движении и при торможении), нули, «замерзание» и NaN на тележке, выбросы ±20 км/ч, шум 1 км/ч, ошибка масштаба +5 %, боксование и юз одной и обеих тележек, блокировка колёс, скачок штампов ±0.5 с, пропадание и «замерзание» команды, одновременное молчание тележек и команды. Обе тележки молчат 30 с: ошибка скорости в окне 0.204 м/с против 2.84 у наивной фузии, смещение пути 3.44 м против 87.5 м (медианы). Флаг проскальзывания на резком боксовании, юзе и блокировке: recall 1.00, время до флага 0.08–0.21 с. Слабые места: docs/RESULTS.md, §6.4.

БЫСТРОДЕЙСТВИЕ: ЗАДЕРЖКА, ЧАСТОТА, РЕСУРСЫ

Замер в том же прогоне чекера организаторов (Docker, весь bag 30618_88aea4d9 в реальном времени, 50 690 входных сообщений): tools/latency_probe.py и tools/resource_monitor.py. Задержка = приход выхода минус приход входного сообщения с тем же header stamp. Первые 2 с bag идёт пачка накопленных сообщений, поэтому перцентили даны после неё, а максимум и с ней.
• Вход → /result/velocity: p50 1.17, p95 2.45, p99 3.03 мс, max 22.8 мс; с учётом стартовой пачки max 32.1 мс.
• Вход → /result/position: p50 1.90, p95 3.23, p99 3.78 мс, max 24.9 мс; с учётом стартовой пачки max 32.4 мс.
• Выходов дольше 100 мс: 0 из 76 949.
• Частота выхода 29.38 Гц; выход на каждый вход, stamp выхода равен stamp входа (38 476 / 38 473 выходов, 0 повторов), покрытие сетки 0.1 с 99.99 %.
• Callback ноды: среднее 0.693 мс, p99 1.995 мс, max 6.32 мс.
• CPU ноды: среднее 0.071 ядра, p95 0.100, max 0.259.
• Память: RSS 62.2 МиБ на старте, max 64.1 МиБ за 22 мин, роста нет; 11 потоков.

Сравнение с ТЗ: задержка ≤ 100 мс (пик ≤ 250 мс): max 32 мс; частота ≥ 10 Гц: 29.4 Гц; ≤ 2 ядра: 0.071 в среднем, 0.259 max; ≤ 0.5 ГБ: 64.1 МиБ. В предварительном прогоне, когда хост параллельно считал офлайн-CV, пик задержки доходил до 202 мс при callback не больше 13.4 мс: это конкуренция за CPU хоста, в чистом итоговом прогоне max 32 мс.
