# Параметры `tram_backup_odometry`

Полный справочник параметров узла `backup_odometry` и офлайн-реплея. Как учтены масса, радиус колеса, момент двигателя и коэффициенты сопротивления из ТЗ — [§1.4](#14-физические-параметры-из-тз).

**Источник истины.** Параметры задаёт dataclass `Params` в
`src/tram_backup_odometry/tram_backup_odometry/core/config.py`. В нём 199 полей, разбитых на 12 групп линейками `# ---- <группа>`.
- В узле ROS 2 каждое поле объявляется как параметр с тем же именем, типом и значением по умолчанию.
- Офлайн-реплей (`replay.py`, `tools/run_cv.py`) использует те же имена.
- Файл `config/params.yaml` **генерируется** из `config.py` (см. [§3](#3-как-переопределить-параметры)). Вручную его не правят.

**Единицы.** Используется СИ: м, с, м/с, м/с², рад. Исключения видны по суффиксу имени: `_kmh` — км/ч, `_deg` — градусы. Скорость колёс в топиках приходит в **км/ч** (analysis_notes timing_units A1). Внутри она переводится в м/с как `v = raw / K`, см. [§2](#2-масштаб-колёс-k_for_vehicle).

**Типы.** В `Params` есть поля `bool`, `int`, `float` и `str`. Узел объявляет параметры с `dynamic_typing=True`, а `Params.from_dict` приводит значение к типу поля:
- `int` → `float` для float-полей;
- `"true"/"1"/"yes"/"on"` → `True` для bool;
- число → строка для `vehicle_id`.

Поэтому записи `acc_max:=2` и `vehicle_id:=30618` корректны.

### 1.1 Точка выхода: `base_link` чекера или мастер-антенна

Публикуемая точка задаётся двумя параметрами. Вдоль пути: `s_route = s_мастер + output_along_offset_m`, где `s_мастер` — положение мастер-антенны на пути (карта, ветка петли или мост). По высоте: `z = z_карты(s_route) + output_z_offset_m`. Сдвиг применяется до перевода в `output_frame`.

| Точка | `output_along_offset_m` | `output_z_offset_m` | Когда |
|---|---|---|---|
| `base_link` (по умолчанию) | `9.873` | `0.0` | Эталон — `/localization/kinematic_state` чекера организаторов. |
| мастер-антенна | `0.0` | `3.10` | Эталон — фиксы мастер-антенны (так оценивают `tools/run_cv.py` и `tools/evaluate.py`). |
| середина базы / ровер | `6.22` / `12.44` | по эталону | Эталон построен по середине базы или по роверу. Высота этих точек отдельно не калибровалась. |

Переключение на мастер-антенну, своим файлом или через `-p`:

```yaml
backup_odometry:
  ros__parameters:
    output_along_offset_m: 0.0
    output_z_offset_m: 3.10
    output_velocity_delay_s: 0.0   # по желанию: физическая скорость на stamp (§1.2)
```

```bash
ros2 run tram_backup_odometry backup_odometry_node --ros-args \
    -p vehicle_id:=30618 -p output_along_offset_m:=0.0 -p output_z_offset_m:=3.10
```

Launch-аргументов для этих параметров нет, см. [§3.2](#32-аргументы-launch).

Выбор точки меняет ошибку на расстояние между точками. Эмуляция чекера, вариант `master_antenna_point` с `output_along_offset_m` 0 и `output_z_offset_m` 3.10, даёт 3D RMSE 10.26 м и z RMSE 3.07 м. У `base_link` это 1.11 м и 0.04 м (`results/checker_30618_88aea4d9/summary.md`). `tools/run_cv.py` всегда оценивает точку мастер-антенны: он подставляет `output_along_offset_m` = 0, `output_z_offset_m` = `z_offset_m` (3.10) и `output_velocity_delay_s` = 0, если их не переопределить через `--set`.

**Начало систем `start` и `enu`.** Это положение мастер-антенны при выставке: x, y и высота GNSS. При выходе в `base_link` первая выходная точка отстоит от нуля примерно на 9.873 м вдоль пути, а её z ≈ `output_z_offset_m` − `z_offset_m` = −3.10 м. При выходе в точке мастер-антенны старт приходится примерно на (0, 0, 0).

### 1.2 Задержка скорости `output_velocity_delay_s`

Если `output_velocity_delay_s` > 0, публикуемая скорость равна оценке фильтра на момент stamp − delay. Её даёт линейная интерполяция по истории скорости за последние ~2 с. Если этот момент позже истории, скорость экстраполируется; если раньше, берётся значение на stamp. Положение публикуется на сам stamp, и параметр на него не влияет.

Значение 0.09 с — **подгонка под эталон, а не физика**. Twist эталона тестового бэга отстаёт от своего stamp примерно на 0.09 с. С задержкой v_rmse чекера 0.0335 м/с, без неё 0.0566 м/с (вариант `no_velocity_delay`, `results/checker_30618_88aea4d9/summary.md`). Подобрано на единственном бэге. Если эталон скорости не запаздывает, например доплеровская скорость GNSS в `tools/run_cv.py`, ставьте `0.0`.

### 1.3 Как выключить GNSS-коррекцию (`gnss_aiding:=false`)

У launch-файла **нет** аргумента `gnss_aiding`. Строку `gnss_aiding:=false` в `ros2 launch` ROS примет без ошибки, но узел её не получит. Выключать нужно параметром узла:

```bash
# без launch
ros2 run tram_backup_odometry backup_odometry_node --ros-args \
    --params-file "$(ros2 pkg prefix tram_backup_odometry)/share/tram_backup_odometry/config/params.yaml" \
    -p vehicle_id:=30618 -p gnss_aiding:=false

# через launch и свой частичный файл
cat > no_aiding.yaml <<'EOF'
backup_odometry:
  ros__parameters:
    gnss_aiding: false
EOF
ros2 launch tram_backup_odometry backup_odometry.launch.py params_file:=no_aiding.yaml vehicle_id:=30618

# офлайн
PYTHONPATH=src/tram_backup_odometry python -m tram_backup_odometry.replay <bag> --set gnss_aiding=false
python tools/run_cv.py --tag my_noaid --set gnss_aiding=false
```

**Что меняется.** С `false` узел уничтожает подписки на GNSS сразу после окончательной выставки. В `/backup_odometry/diagnostics` ключ `gnss_subscribed` становится `False`, режим `nav_gnss` не появляется, а счётчики `pipe_gnss_bursts` и `pipe_gnss_rejected` остаются нулевыми. Положение после выставки ведут одометр и TRN. Скорость побитово совпадает при `true` и `false` (`test/test_gnss_aiding.py`). Остальные `gnss_*` при `false` не действуют.

**Что показывают данные:**

| Проверка | `gnss_aiding: true` | `false` | Источник |
|---|---|---|---|
| Чекер: GNSS по всему бэгу, 3D RMSE | 1.11 м (49 пачек принято, 1 отклонена) | 7.16 м | `results/checker_30618_88aea4d9/summary.md` (`no_gnss_aiding`) |
| Чекер: GNSS только первые 35 с, 3D RMSE | 7.02 м | — | там же (`final_gnss_first_35s_only`) |
| CV: GNSS только первые 10 с, score_loss медиана / среднее | 0.622 / 0.946 | 0.646 / 0.942 | `results/F4_final`, `results/AF_noaiding` |
| CV: GNSS первые 10 с, al_rmse медиана / среднее | 1.98 / 3.15 м | 2.15 / 3.12 м | там же |
| CV: первые 30 с и пачка 1.5 с каждые 120 с, score_loss медиана / среднее | 0.566 / 0.815 | — | `results/F4_final_burst` |

В CV с окном 10 с пачками служат только фиксы после окончательной выставки, т. е. примерно с 3-й по 10-ю секунду. По бэгам коррекция лучше в 26 из 60, хуже в 15, в 19 разница не больше 0.01 (по `per_bag.json` обоих прогонов). Сильнее всего она теряет на `30639_9c362687` (+0.46) и `30639_92226df0` (+0.18); причина не разобрана.

Выключать коррекцию имеет смысл, если после выставки GNSS не должен влиять на положение вовсе (поведение первой версии).

**Режимы `output_frame`.** Код — в `core/frames.py`.
- `map` — система координат pathgraph-карт: UTM 37N (WGS84) минус (300000, 6100000). Совпадает с UTM с точностью ~2 см без поворота и масштаба (map_geometry F1). Этот режим используется по умолчанию, в нём заданы карты, `maps/loops.json` и эталон чекера.
- `utm` — полные координаты UTM 37N: `x + 300000`, `y + 6100000`.
- `start` — `map`, сдвинутый в начальную точку. Начало (x, y, z) — положение мастер-антенны при выставке: медиана опорных фиксов (фиксы в пределах `init_ref_odo_m` пути от последнего), z — медиана высоты GNSS. Смещение выходной точки относительно начала описано в §1.1.
- `enu` — локальная касательная плоскость East-North-Up эллипсоида WGS84. Точка карты переводится в широту и долготу (обратная UTM 37N), затем через ECEF в ENU.
  - Начало берётся в начальной точке при `enu_origin_auto: true`.
  - При `enu_origin_auto: false` начало фиксированное: `enu_origin_lat` / `_lon` / `_alt`. Инициализация его не меняет.
  - От `start` этот режим отличается тремя вещами:
    - сближением меридианов UTM ~1.25–1.33° (`docs/analysis_notes.md`: 1.25°; `docs/MODEL.md`: ≈1.33° в начале ENU), т. е. ~100 м на 4.7 км;
    - масштабом UTM;
    - кривизной Земли по Up.
  - Курс пересчитывается с учётом сближения.
- Неизвестное значение отклоняет `Params.validate()` с `ValueError` при создании `Pipeline`, т. е. при старте узла (см. [§3.3](#33-свой-файл-параметров-или---ros-args--p)).
- В `start` и `enu` (при `enu_origin_auto: true`) начало ставится при каждой инициализации:
  - предварительной, после первого пригодного фикса;
  - окончательной, после окна `init_window_s` = 3 с от первого фикса.

  До окончательной инициализации положение предварительное.

**Нет пригодных фиксов GNSS за `init_timeout_s` (10 с).** Отсчёт идёт по штампам колёс и команды от первого принятого отсчёта колёс. Узел переходит в режим счисления в системе `start`, `frame_id = frame_id_start`: x — пройденный по одометру путь от точки перехода (вдоль начального направления движения), y = z = 0. Этот переход происходит при любом `output_frame`. Если фиксы есть, но их меньше `init_min_fixes`, таймаут закрывает окно и инициализация идёт по имеющимся фиксам.

### 1.4 Физические параметры из ТЗ

ТЗ (обязательные артефакты, п. 3–4) называет массу, радиус колеса, передаточные коэффициенты, момент и коэффициенты сопротивления. Отдельных полей массы, радиуса колеса и момента в `Params` нет. Во входах нет ни массы или загрузки, ни тока или момента двигателя: `src/tram_vehicle_msgs/msg/DriverControllerCommand.msg` несёт только позицию контроллера (`int8`), `VelocitySensor.msg` — только скорость тележки. Поэтому цепочка «позиция → момент на валу → сила на ободе → ускорение», $a = \big(M(n,\omega)\,i\,\eta/r_w - F_{res}\big)/m - g\gamma$ ($M$ — момент, $i$ — передаточное число, $\eta$ — КПД, $r_w$ — эффективный радиус колеса, $F_{res}$ — сопротивление движению, $m$ — масса), не раскладывается на сомножители. Модель идентифицирует удельную силу, то есть ускорение $a(n, v)$, как одну функцию позиции и скорости (`docs/MODEL.md` §4). Вал вращается со скоростью $\omega = i\,v/r_w$, поэтому зависимость момента от $\omega$ — это зависимость карты от $v$.

| Величина из ТЗ | Как учтена | Параметры | Обоснование |
|---|---|---|---|
| Масса $m$ и её изменение (загрузка) | Отдельно не оценивается: масса и загрузка не наблюдаются. Карта $a(n, v)$ — уже сила на единицу массы, подогнанная по всем прогонам. Отклонение массы рейса действует как множитель на тягу и торможение и поглощается усилениями $g_{tr}$, $g_{br}$ (состояния EKF) и смещением модели $b$. Уклон и основное сопротивление на единицу массы от массы в первом приближении не зависят, поэтому усиления стоят только на ветвях тяги и торможения | `gain_tr`, `gain_br` (начальные 1.0), `gain_min` / `gain_max` (0.8 / 1.3), `gain_sigma`, `gain_sigma0`, `gain_adapt`; `bias_enable`, `bias_tau_s`, `bias_sigma` | dynamics D9: усиления по прогонам различаются на ±5–8 %, у 30639 они на 8–11 % выше, чем у 30618; абляция `results/AF_noadapt`: score_loss 1.011 против 0.946 |
| Эффективный радиус колеса $r_w$ | В тяге — внутри карты $a(n, v)$ (сомножитель $i\,\eta/r_w$). В одометрии датчик тележки уже выдаёт скорость в км/ч; отличие фактического радиуса от заложенного в датчик — ошибка масштаба, она входит в $K$: $v = raw/K$, $K$ калиброван по RTK для каждого вагона. Остаток масштаба в рейсе оценивают TRN ($\varepsilon$) и GNSS-коррекция (`pos_eps`); в скорость он по умолчанию не возвращается (`trn_scale_feedback` = false) | `wheel_k_30618` 3.597, `wheel_k_30639` 3.59, `wheel_k` 3.595; `trn_eps_range`, `trn_eps_prior`; `gnss_scale_gain`, `gnss_scale_max` | [§2](#2-масштаб-колёс-k_for_vehicle); $K$ между прогонами и датами меняется до ±1.6 % (`docs/MODEL.md` §3.1) |
| Момент двигателя $M(n, \omega)$, передаточное число $i$, КПД $\eta$ | Не разделяются: $M\,i\,\eta/r_w$ входит в карту тяги целиком. Характеристика привода видна в форме карты: полка $b_0 + a_0 n$ (сила растёт с позицией), общий потолок $A_0$, спад потолка $(v_b/v)^{p_w}$ с ростом скорости ($p_w$ = 1 соответствовал бы постоянной мощности). Динамика привода — чистая задержка и апериодическое звено | `tr_b0`, `tr_a0`, `tr_v1`, `tr_va`, `tr_A0`, `tr_vb`, `tr_pw`; `lag_tr_dead_s`, `lag_tr_tau_s`, `lag_br_dead_s`, `lag_br_tau_s` | dynamics D1, D3; `tools/calibration/fit_dynamics.py` (таблица notch × скорость, `--lag-grid` — задержки), `tools/calibration/fit_traction_params.py` (формулы по таблице) |

## 2. Масштаб колёс: `k_for_vehicle()`

```python
def k_for_vehicle(self):
    if self.vehicle_id == '30618':
        return self.wheel_k_30618      # 3.597
    if self.vehicle_id == '30639':
        return self.wheel_k_30639      # 3.59
    return self.wheel_k                # 3.595 — вагон неизвестен
```

**Что такое K.** Скорость тележки в м/с считается как `v = raw_kmh / K`. Здесь K — «км/ч в топике на 1 м/с истинной скорости».
- При идеальном датчике K = 3.6.
- Калиброванные значения меньше 3.6, т. е. датчик слегка занижает скорость:

  | K | v / (raw/3.6) |
  |---|---|
  | 3.597 (`wheel_k_30618`) | 1.00083 |
  | 3.59 (`wheel_k_30639`) | 1.00279 |
  | 3.585 (медиана RTK для 30639) | 1.00418 |
  | 3.595 (`wheel_k`) | 1.00139 |

- Калибровка сделана по RTK-GNSS (baseline_eval F09).
  - Фолды CV дают 3.5968 и 3.5974 для 30618, 3.5838 и 3.5869 для 30639.
  - Для 30639 взято 3.59, а не медиана RTK 3.585. Перебор K = 3.585…3.605 на 11 оцениваемых прогонах этого вагона (версия F3; `tools/calibration/cv_sweep.py`, результат `.work/scratch_deliv/calib/cv_sweep/wheel_k_30639.json`) дал средний score_loss 1.781 при 3.585, 1.661 при 3.59 и 1.670 при 3.595. Выбор неустойчив между днями записи: майская группа (3 прогона) предпочитает 3.605, августовская (8 прогонов) — 3.59.
  - Отдельные прогоны отклоняются на 1–1.3 %: 92226df0 — 3.634, 253671cc — 3.622 (dynamics D11, anomalies A2).
  - Такой разброс внутри прогона не наблюдаем. В ковариации он учтён как `odo_scale_sigma`. При GNSS-коррекции его частично снимает масштаб положения (`gnss_scale_*`, §5.7).

**Как задаётся `vehicle_id`.**
- Скрытая проверка организаторов идёт на вагоне 30618, поэтому там нужен `vehicle_id:=30618` (`docs/JURY_GUIDE.md`).
- Сравнение строковое и точное: `'30618'` или `'30639'`. Любое другое значение, включая `''`, `'30618.0'` и `'tram1'`, молча даёт `wheel_k`.
- Узел пишет в лог при старте строку `ready: vehicle_id='30618' k=3.5970 ...`. По ней выбранный K легко проверить.
- Launch-аргумент `vehicle_id:=30618` передаётся строкой.
- При `--ros-args -p vehicle_id:=30618` или `vehicle_id: 30618` в YAML ROS прочитает число. Благодаря `dynamic_typing` оно допустимо, а `from_dict` превратит его в `'30618'`.
- Офлайн (`replay.run_bag`, `tools/run_cv.py`) пустой `vehicle_id` берётся из префикса имени бэга. `scripts/run_bag.sh` и `scripts/run_checker.sh` передают его launch-аргументом так же.
- Масштаб выбирается один раз при создании `Pipeline`. Сменить его без перезапуска узла нельзя.

## 3. Как переопределить параметры

### 3.1 `params.yaml` генерируется из `config.py`

Файл `src/tram_backup_odometry/config/params.yaml` записывает `tools/gen_params_yaml.py`.
- Раскладка — `backup_odometry: ros__parameters: ...`.
- Комментарии и группы переносятся из `config.py`.
- Скрипт проверяет обратное чтение: PyYAML и `Params.from_yaml` должны дать `Params()` поле в поле.

Чтобы изменить значение по умолчанию:

```bash
# 1) поправить значение в core/config.py
# 2) перегенерировать и проверить
python3 tools/gen_params_yaml.py            # переписывает config/params.yaml
python3 tools/gen_params_yaml.py --check    # код выхода 1, если файл устарел; иначе "... is up to date (199 parameters)"
# 3) пересобрать пакет (colcon build) — в install/ попадает новый params.yaml
```

Скрипту нужен PyYAML: в окружении ROS 2 он есть (`python3-yaml`), в «голом» `python3` без него скрипт падает с `ModuleNotFoundError: yaml`.

Не правьте `config/params.yaml` вручную: следующая генерация перезапишет правки. Для разовых изменений используйте свой файл параметров (§3.3).

### 3.2 Аргументы launch

```bash
ros2 launch tram_backup_odometry backup_odometry.launch.py \
    [params_file:=<yaml>] [output_frame:=map|utm|start|enu] [vehicle_id:=30618|30639] \
    [maps_dir:=<dir>] [use_sim_time:=false] [log_level:=info]
```

- `params_file` — путь к файлу параметров. По умолчанию берётся установленный `config/params.yaml`.
- `output_frame`, `maps_dir` по умолчанию пустые, `vehicle_id` по умолчанию `30618` (скрытая проверка идёт на этом вагоне). Пустое значение означает «взять из `params_file`». Непустое значение переопределяет файл, потому что `parameters=[params_file, overrides]` применяются по порядку.
- `use_sim_time` передаётся всегда как bool (по умолчанию `false`) и перекрывает значение из файла.
- `log_level` уходит в `--ros-args --log-level`.
- Других аргументов у launch-файла нет. `gnss_aiding`, `loops_enable`, `output_along_offset_m`, `output_z_offset_m`, `output_velocity_delay_s` и остальные задаются своим `params_file` или через `ros2 run ... --ros-args -p` (§3.3). Лишний аргумент вида `gnss_aiding:=false` в `ros2 launch` ошибки не вызывает, но до узла не доходит.

### 3.3 Свой файл параметров или `--ros-args -p`

Все параметры объявлены **read-only**. Поэтому `ros2 param set /backup_odometry <имя> <значение>` у работающего узла завершится ошибкой: параметр только для чтения. Значения задаются **только при старте**:

```bash
# частичный файл: достаточно перечислить изменяемые параметры, остальные возьмутся из Params()
cat > my_params.yaml <<'EOF'
backup_odometry:
  ros__parameters:
    vehicle_id: '30618'
    output_frame: utm
    output_along_offset_m: 0.0      # точка мастер-антенны вместо base_link (§1.1)
    output_z_offset_m: 3.10
EOF
ros2 launch tram_backup_odometry backup_odometry.launch.py params_file:=my_params.yaml

# или напрямую, без launch
ros2 run tram_backup_odometry backup_odometry_node --ros-args \
    --params-file my_params.yaml -p gnss_aiding:=false -p publish_on:=wheels
```

Если имя параметра записано с опечаткой, ROS не объявит такой параметр и **молча** его проигнорирует. Результат проверяйте так:
- по стартовой строке лога `ready: vehicle_id=... k=... output_frame=... publish_on=... maps=...`;
- командой `ros2 param get /backup_odometry <имя>`.

Проверки значений, которые сработают:
- строковые перечисления проверяет `Params.validate()` (словарь `Params.ENUMS`): `publish_on` ∈ `all|cmd|wheels`, `tail_mode` ∈ `decay|straight`, `output_frame` ∈ `map|utm|start|enu`. Сравнение точное, с учётом регистра;
- `validate()` вызывается в конструкторе `Pipeline`, поэтому неизвестное значение останавливает узел при старте с `ValueError: publish_on must be one of all|cmd|wheels, got 'wheel'`. Реплей падает с той же ошибкой, а `run_cv.py` помечает каждый бэг как `error` с этим текстом;
- остальные поля (числа, bool, `vehicle_id`) не проверяются на допустимый диапазон, только приводятся к типу.

### 3.4 Параметр только узла: `maps_dir`

`maps_dir` — каталог с картами `t2s.json` и `s2t.json` и геометрией петель `loops.json`. Узел объявляет его отдельно, в `Params` его нет, в сгенерированном `params.yaml` он упомянут в шапке.
- По умолчанию используется `<share>/tram_backup_odometry/maps`.
- Пустая строка тоже означает значение по умолчанию.
- Задаётся launch-аргументом `maps_dir:=<dir>`, `-p maps_dir:=<dir>` или строкой `maps_dir: <dir>` в своём файле параметров.
- Если `loops.json` в каталоге нет или в нём нет ни одной ветки, узел работает как при `loops_enable: false`: G1-мост и экстраполированный хвост.

### 3.5 Офлайн (реплей и CV)

```bash
# из корня решения; нужны numpy и PyYAML
PYTHONPATH=src/tram_backup_odometry python -m tram_backup_odometry.replay <bag_dir|cache.pkl> [--params my.yaml] [--set key=value ...]
python tools/run_cv.py --tag my_run --bags eval --set trn_enable=false [--params my.yaml] [--jobs N] [--gnss-limit 10] [--gnss-burst 120 1.5]
```

`Params.from_yaml` понимает и плоский словарь, и раскладку `<node>: ros__parameters:`.
- В `Params.from_dict` неизвестный ключ даёт `KeyError`. Это отличается от ROS, где такой ключ молча игнорируется.
- `run_cv.py` передаёт неизвестные ключи как дополнительные атрибуты, чтобы экспериментировать с ещё не заведёнными параметрами. Такие ключи перечисляются в сводке.
- `run_cv.py` оценивает точку мастер-антенны по её фиксам. Поэтому он подставляет `output_along_offset_m` = 0, `output_z_offset_m` = `z_offset_m` и `output_velocity_delay_s` = 0; явный `--set` их перекрывает.
- GNSS в `run_cv.py` подаётся первые `--gnss-limit` секунд (по умолчанию 10) после первого фикса. `--gnss-burst PERIOD DUR` добавляет пачку длиной DUR секунд каждые PERIOD секунд, это проверка GNSS-коррекции.
- Эмуляция чекера на тестовом бэге: `python tools/checker_sim.py --out <dir>`. Варианты `no_gnss_aiding`, `no_loops`, `no_velocity_delay`, `master_antenna_point` и `pre_checker_version` переключают параметры этого документа.

### 5.7 GNSS aiding — коррекция положения по GNSS (19)

Код — `core/pipeline.py` (`_aid_fix`, `_process_burst`, `_s_master`), тесты — `test/test_gnss_aiding.py`. Организаторы разрешили использовать GNSS в середине маршрута для **положения** без штрафа. Скорость GNSS не использует и побитово совпадает с коррекцией и без неё. Выключение — §1.3.

Алгоритм:
1. **Приём фиксов.** После окончательной выставки фиксы мастер-антенны и ровера собираются в пачку. Отбрасываются фиксы со status < 0, с нечисловыми координатами и с (0, 0).
2. **Закрытие пачки.** Пачка закрывается после паузы `gnss_burst_gap_s` (проверяется и на сообщениях колёс и команды) или при `gnss_burst_max_fixes` фиксах.
3. **Привязка фиксов.** Каждый фикс привязывается к показанию одометра на свой штамп по истории `gnss_hist_s`. Фикс ровера сдвигается на `rover_ahead_m`.
4. **Проекция и гейт.** Фикс проецируется на путь (голова, карта, хвост) в окне ±max(`gnss_window_min_m`, `gnss_window_sigma_k`·σ_along) вокруг прогноза. Затем он проходит гейт `gnss_gate_*` по расстоянию до пути.
5. **Проверка согласия.** Невязка вдоль пути ν — медиана по фиксам, разброс — медиана \|ν_i − ν\|. Пачка отклоняется, если разброс больше `gnss_spread_*` или годных фиксов меньше `gnss_min_fixes`.
6. **Якорь.** $k = var_{prior}/(var_{prior} + σ^2)$, $s_{anchor} = s_{pred} + k·ν$, $var_{anchor} = (1 − k)·var_{prior}$.
7. **Публикуемый путь после первой принятой пачки:** $s = s_{anchor} + (1 + ε_{pos})(s_{odo} − s_{odo,anchor}) + Δ_{TRN}$. Дисперсия вдоль пути: $var_{anchor} + (1 − w)(frac·D)^2$, где D — путь от якоря.

Диагностика: режим `nav_gnss`, ключи `pipe_gnss_bursts`, `pipe_gnss_rejected`, `pipe_pos_eps`, `pipe_gnss_nu`, `gnss_subscribed`.

## 6. Выключенные, запасные и условные опции

Эти параметры сохранены для экспериментов, но в поставке не действуют или действуют только в особых случаях:
- `meas_sigma_clip = 0.0`: нижняя граница σ обрезанного измерения выключена намеренно (см. docstring `estimator.py`).
- `trn_sigma_t2s = trn_sigma_s2t = 0.0`: TRN использует общий `trn_sigma`.
- `trn_forget = 1.0`: забывание выключено.
- `trn_scale_feedback = false`: оценка масштаба из TRN не подаётся в выходную скорость.
  - Итоговая абляция `results/AF_scalefb` с включённой опцией даёт средний score_loss 0.933 против 0.946, медиану 0.623 против 0.622, p90 v_rmse 0.0706 против 0.0826 м/с.
  - По бэгам она лучше в 15 из 60, хуже в 8. Больше всего выигрывают `30639_9c362687`, `30639_92226df0` и `30639_253671cc`; у двух последних K отклоняется на 1–1.3 % (§2).
  - В эмуляции чекера этот вариант не прогонялся.
- `bridge_tangent_k = 1.5`: используется только для маршрутов с именами, отличными от T2S и S2T. Для поставляемых карт действуют `bridge_tangent_k_t2s` и `bridge_tangent_k_s2t`.
- `bridge_tangent_k_*`, `sigma0_bridge_*`, `init_bridge_sigma_frac`, `bridge_cross_frac` действуют только при старте вне карты без ветки петли (§5.8).
- `tail_mode`, `tail_curv_decay_m`, `tail_curv_window_m` действуют только без петель (`loops_enable: false` или нет `maps/loops.json`). С петлями после конца ветки хвост идёт прямо.
- `gnss_*` (кроме `gnss_aiding`) действуют только при `gnss_aiding: true`. `loop_*` — только при `loops_enable: true` и наличии `loops.json`.
- `enu_origin_lat` / `_lon` / `_alt` используются только при `output_frame: enu` и `enu_origin_auto: false`.
- `output_velocity_delay_s = 0.09` — подгонка под эталон единственного тестового бэга (§1.2). В CV (`tools/run_cv.py`) она выключена.

## 7. Параметры и известные ограничения

Стресс-тесты `tools/robustness.py` (`results/robustness/summary.md`, §4) показали случаи, на которые влияют параметры этого документа:

| Наблюдение | Параметры | Что происходит |
|---|---|---|
| Молчат все входы 15 с (колёса и команда) | `time_consensus_n`, `time_glitch_s`, `max_gap_s` | `TimeGuard` считает консенсус штампов в сообщениях, а не во времени. Первое сообщение после паузы помечается как скачок вперёд, и первый выход несёт состояние до паузы с новым штампом. |
| Синфазное боксование обеих тележек | `slip_acc_flag`, `slip_hold_s`, `acc_max`, `clip_resync_s` | Флаг держится только на переходе. Затем завышенный согласованный уровень принимается как измерение `both`, и его сдерживает лишь `acc_max`. Конец эпизода обрабатывается неверно. |
| Синфазный юз обеих тележек | `slip_dec_flag`, `slip_hold_s`, `dec_max_consistent` | После `slip_hold_s` плавный заниженный уровень принимается: при `both` без флага допустимо замедление до `dec_max_consistent` = 6 м/с². |
| Постоянная разница масштабов тележек | `agree_rel`, `agree_abs_mps` | Отношение масштабов тележек онлайн не оценивается. Расхождение сверх допуска считается проскальзыванием. |
| «Замёрзшая» команда контроллера | `gain_adapt`, `gain_min`, `gain_max`, `bias_*` | Адаптивные коэффициенты и смещение подстраиваются под неверный вход, в части заездов до границы `gain_min`. |
| Сдвиги часов GNSS на ~1 с | `gnss_hist_s`, `gnss_spread_*` | Фикс привязывается к одометру по своему штампу, и пачка со сдвинутыми штампами даёт невязку вдоль пути ≈ v·Δt. Проверка разброса такой согласованный сдвиг не ловит, гейт проверяет только расстояние до пути. Длительные сдвиги (≈ ±1 с на 18–60 с) есть в 7 из 60 заездов. |
| Торможение не контроллером | `sigma_a_*`, `bias_*` | Модель ускорения и `adhesion_used` его не видят. Скорость держат колёса. |
